# 单元 03：把模糊要求整理成共同目标

[上一单元：先给整件事一个不会混淆的身份](02-one-request-one-work.zh.md) | [返回课程目录](README.md) | [下一单元：从整件事中拿出一次明确委托](04-one-bounded-delegation.zh.md)

## 现在的 Work 里有什么

团队已经有一份编号为 `work-order-cancel-001` 的案卷。

里面保存了陈晨的原始请求，但当前仍是：

```json
{
  "workId": "work-order-cancel-001",
  "epoch": 1,
  "workSpec": null
}
```

林舟不能只看“取消订单”四个字就派人开工，因为还有几个会实质改变实现的问题：

- “未发货”是只看订单状态，还是也要检查仓库是否开始拣货？
- 取消后恢复的是可售库存还是预占库存？
- 谁可以取消，用户本人、客服还是两者都可以？
- “记录原因”保存在哪里，是否允许用户自由输入？
- 上线前需要哪些测试和谁的确认？

这些不是框架能替业务作出的决定。

## 先用普通对话澄清

林舟在同一个 Work 中问：

> “未发货”是否包括仓库已经拣货、但物流状态尚未变成已发货的订单？另外，取消原因是否只使用预设选项？

陈晨回答：

> 已经开始拣货就不能取消。用户只能选择预设原因，客服可以补充内部备注。

这两条仍然是普通 Work 消息。它们很重要，但此时还散落在对话中。

如果周明随后加入，只把最近一条回复拿给他看，他会缺少最初范围；如果只给原始需求，他又会错过新的澄清。

所以团队需要一份“当前共同理解”。

## 先写一张人能读懂的目标卡

在给它正式名字前，先看内容：

```text
想得到什么
  为未发货且尚未开始拣货的订单提供取消能力。

这次改哪里
  订单服务和库存恢复逻辑；不改现有下单接口。

必须遵守什么
  用户只能选择预设原因；客服可以写内部备注；
  生产上线前需要陈晨确认。

怎样算做完
  合法订单可以取消并恢复预占库存；
  已发货或已开始拣货的订单会被拒绝；
  操作原因可以查询；
  同一份最终代码先在测试环境验证；
  同一份最终代码经过另一名成员独立验证。
```

这张卡不是原始消息的替代品。原始消息和澄清仍留在时间线中；目标卡只是把团队现在要据此行动的理解集中起来。

Tiangong 把这份“整件 Work 当前目标说明”叫 **WorkSpec**。

`Spec` 可以理解为 specification，也就是说明书。于是：

```text
Work     = 这整件事以及它的持续身份
WorkSpec = 团队当前认为这整件事要达到什么
```

## 把目标卡写成数据

现在再看结构化形式：

```json
{
  "goal": "允许取消未发货且尚未开始拣货的订单，并安全恢复预占库存",
  "scope": [
    "repository:service-a",
    "订单取消接口",
    "预占库存恢复",
    "取消原因记录"
  ],
  "constraints": [
    "不改变现有下单接口",
    "用户只能选择预设取消原因",
    "客服内部备注不能返回给普通用户",
    "生产上线前需要陈晨确认"
  ],
  "doneWhen": [
    "合法订单可以取消且重复请求不会重复恢复库存",
    "已发货或已开始拣货的订单不能取消",
    "取消原因可以由授权人员查询",
    "同一份最终代码先部署到测试环境并完成验证",
    "最终代码由另一名成员在独立工作区验证通过"
  ],
  "unresolvedAssumptions": [
    "现有库存服务能够按订单释放预占库存"
  ]
}
```

逐组理解：

### `goal`：一句话说明最终意图

它回答“做完以后，业务世界发生什么变化”。它不负责列出每个实现步骤。

### `scope`：这次明确碰哪些范围

范围可以包含仓库、服务、接口或业务区域。它帮助 Leader 和成员避免把相邻问题无限扩张。

### `constraints`：即使能完成，也不能违反什么

例如“不改变现有下单接口”不是最终目标，却会排除一些实现方式。

### `doneWhen`：用普通语言描述怎样才算够了

这里故意不是机器检查编号。它首先服务于 Leader 的语义判断。机器能检查的测试、权限和独立验证要求，会由后面的硬边界另外执行。

### `unresolvedAssumptions`：暂时依赖但尚未完全确认的前提

把假设写出来，比让它藏在模型心里安全。Leader 可以先派一个只读调查，也可以继续向 Human 澄清。

## Work 现在长什么样

Work 当前投影会包含刚形成的 WorkSpec：

```json
{
  "workId": "work-order-cancel-001",
  "teamId": "commerce-team",
  "epoch": 2,
  "workSpec": {
    "goal": "允许取消未发货且尚未开始拣货的订单，并安全恢复预占库存",
    "scope": ["repository:service-a", "订单取消接口", "预占库存恢复", "取消原因记录"],
    "constraints": ["不改变现有下单接口", "生产上线前需要陈晨确认"],
    "doneWhen": ["合法取消会恢复库存", "非法取消会被拒绝", "同一份代码先在测试环境验证", "最终代码经过独立验证"],
    "unresolvedAssumptions": ["库存服务支持按订单释放预占"]
  },
  "createdBy": "human-chen",
  "createdAt": "2026-08-10T09:00:00Z"
}
```

`epoch` 从 1 变成 2，表示有人基于第 1 轮状态完成了一次协调性写入。先不用研究并发实现；第十三单元会用两轮同时作出的 Leader 判断解释它。

## 当前值改变了，旧内容去哪里

WorkSpec 是当前说明，可以随着理解变化而更新。可更新不等于覆盖后不留痕。

形成第一份 WorkSpec 时，系统向 Work 时间线追加一条事件：

```json
{
  "eventType": "work-spec-changed",
  "workId": "work-order-cancel-001",
  "actorId": "leader-lin",
  "reason": "根据陈晨对拣货状态和取消原因的回复形成可执行目标",
  "workSpec": {
    "goal": "允许取消未发货且尚未开始拣货的订单，并安全恢复预占库存",
    "scope": ["repository:service-a", "订单取消接口", "预占库存恢复", "取消原因记录"],
    "constraints": ["不改变现有下单接口", "生产上线前需要陈晨确认"],
    "doneWhen": ["合法取消会恢复库存", "非法取消会被拒绝", "同一份代码先在测试环境验证", "最终代码经过独立验证"],
    "unresolvedAssumptions": ["库存服务支持按订单释放预占"]
  },
  "relatedMessageId": "matrix-event-9010",
  "createdAt": "2026-08-10T09:20:00Z"
}
```

这里保存的是完整的新 WorkSpec，而不是一句“修改了库存规则”。因此数据库损坏当前投影后，系统仍能按时间线找回最后一份完整快照。

注意：这不意味着为每次 WorkSpec 建立一个新的 Work 版本对象。始终只有同一个 `workId` 和一个当前 WorkSpec；时间线负责保留每次完整变化。

## 再发生一次目标变化

实现过程中，陈晨补充：

> 客服取消金额超过 5000 元的订单时，也需要主管确认。

林舟判断这仍属于同一项取消订单能力，而不是另一件独立业务，于是更新当前 WorkSpec。

系统会：

1. 读取当前 Work 和 `epoch: 2`；
2. 形成包含新约束的完整 WorkSpec；
3. 追加新的 `work-spec-changed` 事件；
4. 更新当前投影；
5. 把 epoch 增加到 3；
6. 在一个事务中完成这些写入。

旧事件不修改，也不删除。

## 已经派出去的工作会自动变化吗

不会。

后面我们会看到，每次正式委托都有自己的完整说明。当前 WorkSpec 更新后，它会作为新的背景告诉正在工作的成员，但不能悄悄改写原委托。

如果原委托已经不合适，Leader 应该结束能够安全结束的旧委托，再创建一个新的委托。这样成员不会在执行一半时发现目标被无声替换。

这条区别很重要：

```text
WorkSpec 回答“整件事现在要什么”。
已经派出的具体委托回答“你这一次被要求做什么”。
```

下一单元才会给“具体委托”正式命名。

## 什么时候应该建立新 Work

如果陈晨改口：

> 取消订单先不做了，我们改成自动退款重试。

这不是对取消规则的小调整，而是另一项独立目标。最清楚的处理方式是关闭或取消原 Work，再创建新的 Work。

判断标准不由某个固定关键词决定，而由 Leader 结合语义判断：旧目标的上下文、结果和风险是否仍然构成同一件持续事务。

机器负责保证 Leader 的写入没有并发覆盖；机器不假装能理解两个业务目标是否“本质相同”。

## Human 是否必须逐字确认 WorkSpec

不一定。

一个低风险、表达清楚的请求，可以在 Leader 把理解反馈给 Human 后继续。高风险目标或重大变化，可以由当前控制配置要求 Human 明确确认。

这里的确认表示“Human 认可当前目标理解”，不是允许 Agent 使用任意工具，也不是生产部署批准。生产部署需要另一种绑定精确待执行动作的批准，第十单元会从案例中引入它。

## 常见混淆

### 原始消息等于 WorkSpec 吗

不等于。原始消息是 Human 实际说过的话；WorkSpec 是 Leader 在保留来源的前提下形成的当前共同理解。

### WorkSpec 是实现方案吗

通常不是。它说明目标、范围、约束和完成条件。成员可以在后续的具体委托中探索实现方法。

### WorkSpec 的 `doneWhen` 是自动化测试清单吗

不是。它首先是普通语言的完成指导。机器验证事实会由后续介绍的受控工具回执、独立验证和代码硬检查表达。

### 更新 WorkSpec 会修改已经派出的具体委托吗

不会。每一份具体委托在创建时就已经固定。

### WorkSpec 更新是不是创建第二个 Work 版本对象

不是。当前设计保留同一个 Work，在时间线中追加完整快照，并更新当前投影。
