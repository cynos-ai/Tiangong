# 单元 02：先给整件事一个不会混淆的身份

[上一单元：一条消息怎样走到 AI 团队](01-message-to-team.zh.md) | [返回课程目录](README.md) | [下一单元：把模糊要求整理成共同目标](03-clarify-the-goal.zh.md)

## 先回到刚收到的消息

林舟已经收到陈晨的请求：

> 给商城增加取消订单功能。只有未发货订单可以取消；取消后恢复库存并记录原因；不要改变现有下单接口。先在测试环境验证，上线生产前让我确认。

最直接的实现似乎是：把这句话放进模型上下文，然后让林舟开始工作。

先别急着给任何东西起名字。想象接下来几天群里还会发生什么：

- 陈晨补充“仓库已经拣货的订单也不能取消”；
- 林舟报告当前进度；
- 另一个人询问昨天的支付故障；
- 周明提交实现结果；
- 陈晨又提出一个完全无关的退款需求。

如果系统只有一段不断变长的聊天历史，就必须反复猜测：哪句话属于哪件事？昨天的补充是否仍然有效？退款需求是不是取消订单的后续？

## 第一种朴素办法：按聊天房间分组

我们可以说，一个房间里的消息都属于同一件事。

但一个真实团队经常在同一房间讨论很多工作。反过来，同一件工作也可能跨越多天、多个线程，甚至包含附件和系统通知。

所以“房间”解决的是消息投递位置，不是业务事务身份。

## 第二种朴素办法：拿第一句话当标题

我们也可以把第一条消息当作整件事的唯一标识。

这仍然有问题：

- 两个人可能发送相同文字；
- 同一条消息可能因网络重试被处理两次；
- 后续消息需要一个稳定地址才能明确关联回来；
- 需求被澄清后，第一句话不再等于当前理解；
- 关闭后收到的新要求不应该悄悄重开旧事务。

我们真正缺少的不是更聪明的标题，而是一个独立的“案卷编号”。

## 先建立一个空案卷

Tiangong 把这样一件可持续跟踪的完整事务叫 **Work**。

可以先用一句中文记住：

> Work 是“这整件事”的身份和持续上下文，不是需求正文，也不是一次具体执行。

收到请求时，系统可以先创建一份很小的 Work 记录。里面的 `workSpec` 字段留给“团队当前整理出的目标说明”，下一单元会再给它完整解释；现在的 `null` 只表示目标尚未形成。

```json
{
  "workId": "work-order-cancel-001",
  "teamId": "commerce-team",
  "epoch": 1,
  "workSpec": null,
  "createdBy": "human-chen",
  "createdAt": "2026-08-10T09:00:00Z"
}
```

先逐行读，不需要猜：

| 字段 | 在案例里表示什么 |
|---|---|
| `workId` | 这份案卷自己的稳定编号，以后消息、委托和结果都能回到它 |
| `teamId` | 哪个团队负责这件事 |
| `epoch` | 当前案卷被协调性修改了多少轮；现在只把它当作防止并发覆盖的计数器 |
| `workSpec` | 团队当前整理出的目标说明；`null` 表示还在澄清，尚未形成 |
| `createdBy` | 最初由谁触发创建 |
| `createdAt` | 何时创建 |

## 为什么一开始允许目标为空

这不是遗漏，而是刻意设计。

现实中的第一句话经常不完整。例如陈晨可能只说：

> 帮我把订单取消做一下。

如果系统为了创建 Work 而立刻编造适用范围、完成条件和上线要求，就把模型猜测伪装成了用户事实。

更诚实的做法是：

1. 先承认“收到了一件新事情”；
2. 为它分配稳定身份；
3. 把原始消息保存进时间线；
4. 允许目标说明暂时为空；
5. 由 Leader 继续澄清。

在 `workSpec` 仍为 `null` 时，系统不允许派发正式具体委托。这样团队可以讨论，但不能把尚未说清的猜测变成团队成员必须执行的任务。

## 原始消息放在哪里

Work 不是只保存当前摘要。它还有一条按顺序追加的时间线，用来记录与这件事有关的消息和重要变化。

第一条时间线记录可以这样理解：

```json
{
  "eventType": "human-message-received",
  "workId": "work-order-cancel-001",
  "actorId": "human-chen",
  "platformMessageId": "matrix-event-9001",
  "text": "给商城增加取消订单功能……上线生产前让我确认。",
  "createdAt": "2026-08-10T09:00:00Z"
}
```

这条记录回答的是：

- 谁说了什么；
- 消息来自哪个经过认证的平台事件；
- 它被归入哪一件 Work；
- Tiangong 何时接收。

它没有回答“团队最终决定怎么理解”。那是下一单元才会形成的内容。

## 同一条消息为什么不能创建两件 Work

网络并不总是只投递一次。Worker 可能在保存成功后、回复成功前崩溃；上游随后再次发送同一平台事件。

如果每次收到都新建 Work，陈晨的一条请求会变成两件并行事务。

因此入口使用平台消息身份去重：

```text
第一次看到 matrix-event-9001
→ 创建 Work 和第一条时间线记录

再次看到同一个 matrix-event-9001
→ 返回已经创建的 Work
→ 不再创建第二份
```

这里的重点不是某个数据库写法，而是语义：同一条已认证输入的重放，必须回到同一结果。

## 后续消息怎样决定放到哪里

Tiangong 使用一个偏保守的规则。

### 明确关联到仍然打开的 Work

例如陈晨在 Work 的线程中回复：

> 补充一下，仓库已经开始拣货的订单也不能取消。

平台关联清楚，系统就把消息追加到现有 Work 的时间线。

### 没有明确关联

例如陈晨在主房间另发：

> 退款失败也需要做一个自动重试。

系统不会因为主题都和订单有关，就让模型猜它属于取消订单。没有清楚关联时，默认创建新的 Work。

### 关联有歧义

如果一句“这个也改一下”可能指向两件正在进行的工作，系统同样宁愿建立新 Work，再让 Leader 澄清，也不把两段上下文悄悄混合。

这个选择看似会多建一点记录，但它避免了更危险的问题：一个 Work 中的权限、目标或代码上下文泄漏到另一个 Work。

## Work 不是哪些东西

### Work 不是聊天房间

一个房间可以承载多个 Work。Work 使用平台消息，但不以房间作为业务身份。

### Work 不是一段需求 JSON

当前目标会被放进 `workSpec`，但 Work 还连接时间线、具体委托、成员交回的成果、受控外部操作和最终决定。

### Work 不是一次具体委托

“交付取消订单能力”是一整件事；“在 service-a 中实现取消接口”只是其中一次委托。后者将在第四单元出现。

### Work 不是 Agent 会话

模型会话可以被清理、压缩或重建，Work 仍然存在。业务事实不能只活在聊天记忆里。

### Work 创建不表示已经开工

此刻 `workSpec` 仍可能为空，没有正式具体委托，也没有成员在修改代码。系统只确认：收到了一件需要持续处理的事情。

## 到目前为止怎样查找

如果你知道平台消息 ID，可以查它创建或关联了哪个 Work：

```text
matrix-event-9001
→ work-order-cancel-001
```

如果你知道 Work ID，可以先取当前投影，再列出时间线：

```text
work-order-cancel-001
├─ 当前投影：team、epoch、当前 workSpec
└─ 时间线：原始请求、补充消息、后续重要变化
```

这里的“当前投影”只是把历史折叠成方便读取的当前样子。第三单元会具体看到目标如何形成和更新。

## 本单元的心智模型

可以把 Matrix 房间想成一张很长的公共桌面，把 Work 想成桌面上一个有编号的文件夹。

消息仍然来自公共桌面，但一旦确认属于某件事，就会被放入对应文件夹。文件夹刚建立时可以只有原始纸条，不必假装里面已经有完整方案。
