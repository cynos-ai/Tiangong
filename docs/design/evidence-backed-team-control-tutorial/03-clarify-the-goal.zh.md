# 单元 03：把模糊需求整理成当前目标

[上一单元：先给整件事一个稳定身份](02-one-request-one-work.zh.md) | [返回课程目录](README.md) | [下一单元：从整件事中拿出一次明确委托](04-one-bounded-delegation.zh.md)

## 现在有案卷，还没有可执行目标

`work-order-cancel-001` 已经存在，原始消息也在时间线中：

```json
{
  "workId": "work-order-cancel-001",
  "epoch": 1,
  "workSpec": null
}
```

但林舟仍然不知道：

- “未发货”是否包含已经开始拣货；
- 恢复可售库存还是释放预占库存；
- 用户和客服可以填写什么取消原因；
- 是否必须修改数据库；
- 测试环境验证到什么程度；
- 陈晨说的“上线前确认”应绑定哪一次部署。

这些问题会改变代码和外部动作，不能靠模型默认值补齐。

## 澄清首先是普通对话

林舟在同一 Work 中问：

> 仓库已经开始拣货、但物流状态仍是未发货的订单，能取消吗？用户可以自由填写原因吗？

陈晨回答：

> 开始拣货就不能取消。用户只能选预设原因，客服可以补内部备注。

两条消息都进入 Work timeline。它们是 Human 实际说过的话，不需要先变成特殊审批对象。

此时有两个常见错误。

### 错误一：只把最新回复交给成员

成员会缺少原始范围和“不改下单接口”等约束。

### 错误二：每次把整个聊天记录塞进上下文

聊天里可能混有推测、撤回意见、无关讨论和很长历史。模型还要自己判断哪一句代表当前理解。

团队需要一份简洁的“当前目标卡”，同时保留原始消息作为来源。

## WorkSpec 是整件 Work 的当前目标卡

Tiangong 把 Leader 对整件 Work 当前理解的简洁说明叫 **WorkSpec**。

```text
Work     = 这整件事的持续身份和历史
WorkSpec = Leader 当前认为整件事要达到什么
```

案例中的 WorkSpec 可以是：

```json
{
  "goal": "允许取消未发货且尚未开始拣货的订单，并安全释放预占库存",
  "scope": [
    "repository:service-a",
    "订单取消接口",
    "预占库存释放",
    "取消原因记录"
  ],
  "constraints": [
    "不改变现有下单接口",
    "用户只能选择预设取消原因",
    "客服内部备注不能返回给普通用户",
    "部署生产前需要陈晨对精确操作作决定"
  ],
  "doneWhen": [
    "符合条件的订单可以取消且重复请求不会重复释放库存",
    "已发货或已开始拣货的订单会被拒绝",
    "授权人员可以查询取消原因",
    "目标代码已在测试环境验证"
  ],
  "unresolvedAssumptions": [
    "库存服务支持按订单幂等释放预占库存"
  ]
}
```

## 每组字段怎样使用

### `goal`：最终想改变什么

它描述业务结果，而不是实现步骤。不要写成“先改 controller，再加 repository，再跑测试”。实现方法留给 Agent。

### `scope`：这次明确覆盖哪里

范围帮助 Leader 防止任务无限扩张，也帮助成员知道哪些代码和业务区域与当前 Work 相关。但它仍不授予机器访问权；真正仓库能力来自后面的配置和 runtime binding。

### `constraints`：无论怎样实现都不能违反什么

例如“不改下单接口”会排除某些方案。“生产部署前精确确认”描述 Human 需求，但真正授权仍要由 Operation 和 Approval 代码完成。

### `doneWhen`：Leader 判断完成时要考虑什么

它用人能读懂的语言描述完成方向，不是机器 criterion ID，也不是 Kernel 流程节点。Leader 可以据此判断是否还要派 review、测试或集成 Task。

### `unresolvedAssumptions`：目前依赖但没确认的前提

显式写出假设，Leader 才能选择继续询问 Human、派只读调查 Task，或接受有限风险继续。假设不能悄悄变成事实。

## WorkSpec 不授予机器权限

假设 WorkSpec 中写：

```text
需要读取生产数据库确认历史订单。
```

这句话只表达业务想法。它不能：

- 把生产凭据送进 Worker；
- 修改 MemberConfig；
- 放宽网络；
- 绕过外部 Adapter；
- 让普通 Bash 连接生产。

语义目标与机器能力分开，是整套设计最重要的边界之一。

## 当前目标怎样写入而不丢历史

形成 WorkSpec 时，系统追加一个 `work-spec-changed` timeline fact：

```json
{
  "eventType": "work-spec-changed",
  "workId": "work-order-cancel-001",
  "actorId": "leader-lin",
  "reason": "根据陈晨对拣货状态、库存类型和原因范围的回复形成当前目标",
  "workSpec": {
    "goal": "允许取消未发货且尚未开始拣货的订单，并安全释放预占库存",
    "scope": ["repository:service-a", "订单取消接口", "预占库存释放"],
    "constraints": ["不改变现有下单接口", "部署生产前需要精确确认"],
    "doneWhen": ["合法取消会释放一次预占库存", "非法取消会被拒绝", "目标代码已在测试环境验证"],
    "unresolvedAssumptions": ["库存服务支持幂等释放"]
  },
  "relatedMessageId": "message-9010",
  "createdAt": "2026-08-10T09:20:00Z"
}
```

同一个事务还会：

1. 把 Work 当前投影的 `workSpec` 更新为这份完整内容；
2. 把 `epoch` 从 1 增加到 2。

时间线事件是历史事实，当前投影是读取便利。两者不是两套独立真相：投影只是最后一份完整事件的事务性当前视图。

## 为什么每次都保存完整快照

假设只记录：

```text
“增加拣货限制”
```

恢复时必须正确重放所有局部补丁，还要处理字段删除、顺序和旧格式。更简单可靠的办法是每次 `work-spec-changed` 保存完整新 WorkSpec。

这不等于建立 `WorkSpecVersion` 对象。系统仍然只有：

```text
一个 Work ID
一条追加时间线
一个当前 WorkSpec 投影
```

## 目标改变时怎样处理

实现开始后，陈晨补充：

> 客服取消金额超过 5000 元的订单时，还需要主管确认。

林舟判断它仍属于同一取消订单 Work，于是形成包含新约束的完整 WorkSpec，并追加下一条 `work-spec-changed`。

如果陈晨改成：

> 取消订单不做了，改成退款失败自动重试。

这更像另一件独立事务。Leader 可以 `stop-work` 结束原 Work，再由新消息创建新 Work。Kernel 不用关键词自动判断“是不是同一业务”，这是 Leader 的语义责任。

## 已派发 Task 会自动收到新目标吗

不会。

一个已经派发的 Task 有不可变 TaskSpec。WorkSpec 后来改变时，Leader有三种选择：

1. 与该 Task 无关，不发任何内容；
2. 只是有帮助的背景，通过明确的定向消息发送，并标成非权威背景；
3. 实质改变原委托，安全取消旧 Task，再创建新 Task。

成员可以主动查询当前 Work 摘要，但查询结果也只是背景，不能把旧 TaskSpec 悄悄改掉。

为什么这样保守？因为自动注入新 WorkSpec 会让成员在执行一半时不知道自己究竟被委托了哪一版目标，工具调用和最终报告也失去明确语义。

## 等待 Human 时系统做什么

如果关键问题没有安全默认值，系统应：

- 清楚通知陈晨需要回答什么；
- 停止没有意义的模型循环和本地计算；
- 可以释放逻辑 session；
- 允许发送有界、去重的提醒；
- 让 Work 保持打开；
- 不因为时间过去而编造答案。

UI 可以显示“等待 Human”，但这只是根据消息和定时器推导的标签，不是新的业务状态对象。

澄清不是 Approval。它帮助 Leader理解目标，但不能直接授权部署、数据库写入或外部通知。

## WorkSpec 是否必须让 Human 点一次“确认”

Kernel 不统一要求。

林舟可以把理解反馈给陈晨，继续普通沟通。某个专业 Skill 或外部流程可以要求客户验收目标，但通用 Kernel 不建立强制 Human 关闭签字事件。

真正危险的外部写入会在第 10 单元通过精确 Operation Approval 处理。那是对具体动作授权，不是对一份目标摘要泛泛点头。
