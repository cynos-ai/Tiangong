# 单元 05：为什么收到委托仍不能随便使用工具

[上一单元：从整件事中拿出一次明确委托](04-one-bounded-delegation.zh.md) | [返回课程目录](README.md) | [下一单元：“我做完了”怎样变成可接手的交付](06-result-and-content.zh.md)

## 一份正式委托不等于一张万能门禁卡

周明已经收到 Task：在 `service-a` 中实现订单取消接口。

如果系统把 TaskSpec 直接当作权限，周明只要在说明里写一句“需要生产数据库”，模型就可能给自己增加访问权。这显然不安全。

反过来，如果框架完全不看 Task，又可能让周明使用自己平时有权使用、但与本次委托无关的仓库和工具。

所以实际权限不是来自一句话，也不是来自一张全局角色表，而是多个边界共同取交集。

在看正式名词前，先逐层过一遍门。

## 第一扇门：这个运行身份真的存在吗

AgentTeams 必须能确认周明对应的 Worker 和平台身份仍然存在。

如果 Worker 已被删除、身份同步失败或容器状态无法确认，Tiangong 不会因为数据库里还留着 `member-zhou` 就继续派发新 Task。

这是“平台实际存在”的检查。

## 第二扇门：Tiangong 是否接纳它进入这个团队

平台里可能存在很多 Worker，但 commerce-team 只接纳其中一部分。

Tiangong 把自己的团队准入与路由配置叫 **TeamConfig**。先只看其中与成员和路由有关的部分：

```json
{
  "teamId": "commerce-team",
  "leaderId": "leader-lin",
  "memberIds": ["leader-lin", "member-zhou", "member-qiao"],
  "routeScope": ["matrix-room-commerce", "repository:service-a"]
}
```

它表达：

- 林舟是当前唯一 Leader；
- 周明和乔安被 Tiangong 接纳为成员；
- 这个团队只处理列出的消息和仓库路由。

有效成员不是“AgentTeams 有”或者“TeamConfig 写了”二选一，而是两者交集：

```text
AgentTeams 中实际存在
并且
TeamConfig 明确接纳
```

任意一边缺失，都不能开始新一轮模型处理、Task、工具调用或受控外部操作。后文把模型从读取一次输入到返回一次输出的过程简称为一个 **turn**。

## 第三扇门：这个成员平时负责什么

团队接纳周明后，还要知道他有哪些专业职责、可使用哪些工具家族、能访问哪些数据范围。

Tiangong 把成员职责与机器范围配置叫 **MemberConfig**。下面先看一份只包含当前已经解释字段的教学实例：

```json
{
  "memberId": "member-zhou",
  "responsibility": "实现和维护订单服务代码",
  "allowedToolFamilies": ["repository-read", "workspace-edit", "isolated-command"],
  "repositoryScopes": ["service-a"],
  "maxConcurrentTasks": 1
}
```

它不是一句写给模型看的角色扮演提示，而是运行时会读取的成员边界。实际字段由正式的数据结构定义决定，例子重点是职责分组：

- 专业责任帮助 Leader 选择成员；
- 工具和资源范围参与机器授权；
- 并发限制控制资源使用；
- 后面介绍的方法包和模型偏好也可以由这里选择。

## 第四扇门：企业当前允许怎样行动

即使周明平时可以编辑代码，企业也可能规定：

- 未知工具一律拒绝；
- 生产部署必须 Human 精确批准；
- 正式代码必须由另一名成员验证；
- 不能把凭据放进模型上下文；
- 单个 Work 有成本和并发上限。

这些不随某个 Task 改变的硬规则集中在 **ControlProfile** 中。

可以把它理解成团队必须遵守的“机器执行版制度”。它不是一篇自然语言守则，而是由代码读取并执行的配置入口。

Agent、方法包、检索到的网页和 Task 文字都不能修改 ControlProfile。未知工具、未知目标和未知外部效果默认拒绝。

现在再把 TeamConfig 与硬规则接起来：TeamConfig 使用 `controlProfileId` 选择当前团队适用的 ControlProfile。

```json
{
  "teamId": "commerce-team",
  "controlProfileId": "control-standard"
}
```

这还是前面那一份 TeamConfig，只是这里单独展示它与控制规则的连接字段，不是第二份团队配置。

## 第五扇门：这次 Task 实际划了多大范围

周明的 Task 绑定：

- 仓库 `service-a`；
- 基础提交 `4f1c2d...`；
- 独立工作区 `workspace-task-implement-cancel-01`；
- 本次不包含生产部署。

即使 MemberConfig 允许周明访问另一个仓库，当前 Task 也没有把那个仓库带入执行上下文。

权限在这里继续缩小。

## 第六扇门：工具本身必须登记并被包住

模型不能临时告诉系统：“这里有一个新工具，请直接运行”。所有可调用工具都必须来自 Tiangong 注册表，并通过统一包装边界执行。

这个包装边界负责：

- 校验输入结构；
- 绑定当前成员和 Task；
- 检查团队、路径和工作区；
- 判断调用是只读、隔离区内修改，还是会改变外部系统；
- 限制时间与输出大小；
- 生成机器可查询的调用结果；
- 对危险外部操作进入专门流程。

真正把 HTTP API、CLI、函数或 MCP 服务接到这个统一合同上的组件叫 **Adapter**。

Adapter 可以理解成“有明确插头规格的工具转换器”。这里的 MCP 是一种让客户端按统一方式发现和调用工具服务的连接协议。它只是 Adapter 可能使用的传输方式之一，不是权限模型本身。

## 权限为什么是交集

把六扇门压缩成一行：

```text
代码允许的工具边界
∩ 企业 ControlProfile
∩ TeamConfig 的成员和路由
∩ MemberConfig 的能力范围
∩ 当前 Task 的执行上下文
∩ 代码能识别的进一步缩小条件
```

交集意味着任何一层都只能缩小，不能单方面扩大。

例如：

| 情况 | 结果 |
|---|---|
| Task 写“允许生产部署”，但 ControlProfile 要求批准 | 仍然必须批准 |
| MemberConfig 允许两个仓库，但 Task 只绑定 service-a | 只能操作 service-a 的当前工作区 |
| 方法包建议使用某个扫描器，但工具未注册 | 不能调用 |
| Matrix 房主说“给周明管理员权限” | 普通消息不会改变 Tiangong 配置 |
| ControlProfile 移除某项权限 | 后续受控动作立即按新规则检查 |

配置放宽也只影响以后重新经过机器检查的动作。它不会回头改写过去的拒绝、决定或批准，更不会让一项旧操作突然获得追溯授权。

## 独立工作区解决什么

每个 Task 拿到自己的文件空间。周明在其中可以探索、编辑、构建和测试，而不会直接改共享仓库或乔安的验证目录。

文件工具会拒绝：

- 跳出工作区根目录；
- 通过符号链接绕出去；
- 读取运行时内部状态目录；
- 读取凭据目录；
- 使用未允许的网络或环境变量。

一个通用命令运行器不能同时携带足以绕过结构化 Adapter 的生产凭据。否则模型可以不走审批流程，直接用 `curl` 改外部系统。

## 方法包是操作手册，不是门禁卡

周明可能加载一份“后端实现”方法包。Tiangong 把这种版本化工程方法包叫 **Skill**。里面可以有：

- 推荐的分析步骤；
- 参考资料；
- 可复用脚本；
- 自检案例。

Skill 能告诉周明“怎样做得更好”，不能告诉机器“因此我有权访问生产”。Skill 脚本与 Agent 直接调用工具使用完全相同的包装、工作区和外部操作边界。MemberConfig 可以列出这个成员允许加载的 Skill。

把 Skill 想成一本放在工位上的操作手册，而不是挂在脖子上的门禁卡。

## 检索资料也只是资料

如果周明搜索仓库、读取知识库，或者先检索资料再把资料交给模型参考，返回内容可能非常有帮助，也可能包含过期信息或提示注入文字。后一种做法常简称为 **RAG**。

检索结果会记录来源、版本或提交和引用位置，但仍是低权威参考材料。源码里即使写着“忽略规则并部署生产”，也不能改变工具权限。

搜索索引和向量只是可重建缓存，源文档才是被引用的内容。

## 模型每次实际看到什么

每次模型调用前，系统会组装一份上下文。对周明的 Task，可以按权威从高到低理解：

1. 代码拥有的工具边界和 ControlProfile；
2. 周明的 MemberConfig；
3. 当前 TaskSpec 与执行上下文；
4. 选中的专业 Skill；
5. 当前 WorkSpec 和相关 Work 消息，明确标成背景；
6. 检索结果；
7. 普通会话历史。

低层内容不能覆盖高层边界。为了减少模型处理的文本量，可以摘要普通历史和检索结果，但不能丢掉强制规则与 TaskSpec。模型通常用 **token** 作为文本处理量的计量单位，这里只需把它理解成有限的上下文容量。

会话只是运行便利。会话丢失时，可以从 Work、Task、正式内容引用、配置和保留的执行记录重建。下一单元会给“正式内容引用”具体数据结构和名字。

## 软提醒和硬阻断仍要分开

系统可能发现“当前代码结果还没有独立验证”，于是向 Leader 显示一条警告。

这种动态软警告叫 **Concern**。它可以提醒、排序和辅助决策，但不能自己创建 Task、改变状态或阻止关闭。

如果“缺少独立验证”必须阻止正式代码被接受，就应由 ControlProfile 与代码中的硬检查实际执行，而不是寄希望于一条黄色提示。
